This design document covers my B+Tree implementation for Project 2, including tombstones, tree operations, iteration, and concurrency control.

**Author:** Yueqi Ren

## Tombstones

I use the tombstone layout from the starter code: `num_tombstones_` and a fixed array `tombstones_` that stores indexes into the key-value arrays. I keep the oldest tombstones at the front. `RemoveKeyVal` appends an index to this buffer. The page size does not change unless the buffer is already full or `NumTombs` is 0. If the buffer is full, I physically delete the oldest tombstoned entry to make room. If `NumTombs` is 0, I delete the key immediately.

I added `RemoveTombstone` and `DeleteTombstone`. `RemoveTombstone` removes an index from the tombstone buffer, shifts the later indexes forward, and decrements the count. I use it when an insertion finds that the key is already stored as a tombstoned entry, so I can restore the key in place with an updated value.

`DeleteTombstone` physically removes the entry by calling `DeleteKeyVal` at the stored index. This shifts the key-value arrays and updates the remaining tombstone indexes. It then calls `RemoveTombstone` to remove the index from the buffer. When the buffer is full, I evict `tombstones_[0]` if `RemoveKeyVal` or a tombstone insertion during borrowing or merging needs another slot.

## B+Tree Operations

### Point search

Point search does not modify the tree, so I traverse the tree using hand-over-hand locking with read guards until I reach the leaf. I then iterate through the entries, skipping tombstoned entries. If I find the key, I add its value to the output and return `true`. Otherwise, I return `false`.

### Insertion

I first use optimistic latching to traverse the tree and find the target leaf. If the leaf is safe, I insert the key-value pair and return. Otherwise, I release the guards and restart from the root using pessimistic write latch crabbing.

Unlike the recommended leaf split strategy, I split when adding a new entry would exceed the page's maximum size. I distribute the existing entries and the new entry directly between two pages to avoid overflowing the original array. I propagate splits from the bottom up until a parent has room for the new separator and child pointer. If the root splits, I create a new internal root pointing to the two resulting pages and update the root page ID in the header.

### Deletion

I use optimistic and pessimistic latching similarly to insertion. If the key does not exist or is already tombstoned, I return immediately. After deletion, I rebalance underfull pages from the bottom up. I first try borrowing from the left sibling, then the right sibling, using only siblings with the same parent. If borrowing is not enough, I try merging with the left sibling, then the right sibling. In either case, I keep the left page and remove the right page.

I use a loop for borrowing because moving a tombstoned entry into a page with a full tombstone buffer can trigger a physical deletion, leaving the receiving page underfull. I continue borrowing until the page reaches its minimum size or neither sibling can safely provide more entries.

## Index Iterator

My iterator stores a shared pointer to a read guard for the page it is currently reading. To advance the iterator, I first move to the next key-value pair within the current page, skipping tombstoned entries. If I reach the end of the page, I move to the next page using hand-over-hand locking. I acquire the read guard for the next page before releasing the current guard.

## Concurrency Control

I acquire locks from the top of the tree to the bottom and from left to right when locking leaf pages. I follow the top-to-bottom order when traversing the tree for search, insertion, and deletion. I follow the left-to-right order when scanning with the iterator and when borrowing or merging entries between siblings. During traversal, I release ancestor guards once I have acquired the next guard and confirmed that the operation no longer needs those ancestors.
