## Context and Scope

A B+Tree supports point lookups and ordered scans without searching every row in a table. Project 2 builds this index on top of the buffer pool and page guards from Project 1. The required components are page layouts, insertion and deletion, point search, an iterator, and concurrency control. See the [original Project 2 specification](https://15445.courses.cs.cmu.edu/fall2026/project2/).

The index supports unique keys and must preserve its structure as pages split, merge, or redistribute entries. Leaf pages buffer deletions as tombstones, so searches and scans must distinguish live entries from entries awaiting physical removal. Concurrent operations use page-level latches rather than locking the entire tree. These requirements shape the design below, particularly how I maintain tombstones during rebalancing and decide when ancestor latches can be released. The [specification](https://15445.courses.cs.cmu.edu/fall2026/project2/) defines these constraints.

## Internal Pages and Leaf Pages

Each tree node occupies one page managed by the buffer pool. An **internal page** stores separator keys and child page IDs. The separators divide the keys into ranges and tell a search which child to follow. For example, separators `20` and `40` divide three children into keys below `20`, keys from `20` up to but not including `40`, and keys at least `40`. There is one more child pointer than separator; in this layout, the first key slot is unused.

A **leaf page** stores sorted key-value pairs, where each value is a record ID identifying a tuple. It also points to the next leaf, so a scan can move through the keys in order without returning to the root. Internal pages provide routing information; leaf pages hold the index entries returned to the caller.

### Leaf pages with tombstones

The leaf pages in this project also have a fixed buffer of **tombstones**: indexes of entries that are logically deleted but still occupy space in the key-value arrays. Searches and scans skip these entries. For example, deleting `20` from `[10, 20, 30]` can record index `1` as a tombstone while leaving all three entries in place. The page's stored size still counts all three entries.

I keep the tombstone count in `num_tombstones_` and the indexes in `tombstones_`, oldest first. `RemoveKeyVal` appends an index. If the buffer is already full, it first physically removes the oldest tombstoned entry to make room. With `NumTombs == 0`, deletion removes the entry immediately. This delays array shifts, but means that a logically deleted entry still uses a slot until it is physically removed.

The helpers handle two different cases. `RemoveTombstone` removes only the deletion marker, allowing insertion to restore an existing key with an updated value. `DeleteTombstone` calls `DeleteKeyVal` to remove the entry itself; that helper shifts the arrays, adjusts the remaining tombstone indexes, and removes the associated marker. Splitting and moving entries must also carry their tombstone state to the new positions.

## B+Tree Operations

### Point search

I start with the root page ID stored in the header. If there is no root, the search returns `false`. At each internal page, `SearchInternal` uses binary search on the separators to choose the child whose range contains the key. Equality follows the child to the right of that separator. I repeat this until I reach a leaf, then scan its entries for a matching key, skipping tombstones. A match adds its record ID to the result and returns `true`; otherwise, the search returns `false`.

Search only needs read guards. I acquire the next page's guard before releasing the current one, so the path remains protected while moving between pages. This is hand-over-hand locking.

### Insertion

Insertion follows the same separators to find the target leaf. I first traverse with read guards, then acquire a write guard on the leaf while still holding its parent's read guard. An existing live key is rejected; a tombstoned key is restored in place. If there is a free slot, I insert the new pair in sorted order and finish without changing any ancestors. An empty tree starts with a single leaf as its root.

If the leaf is full, I release the guards and restart with write guards, retaining the ancestors that may need to change. This optimistic first attempt keeps ordinary insertions local to the leaf; the second pass handles structural changes.

I split only when the new entry would exceed the page's maximum size. I distribute the existing entries and the new pair directly between two leaves, avoiding a temporary array overflow, and link the new right leaf into the leaf chain. Its first key becomes the separator inserted into the parent alongside its page ID. If the parent is also full, I split it and continue upward. If the root splits, I create a new internal root and update the header's root page ID.

### Deletion

Deletion first finds the target leaf using the same optimistic traversal as insertion. Within the leaf, `FindKey` uses binary search and treats tombstoned keys as absent. If the key is absent, I return. Otherwise, I check whether deletion can finish within the leaf. Adding a tombstone usually leaves the stored size unchanged, but a full tombstone buffer forces a physical removal. If deletion could leave the page below its minimum size, I restart with write guards on the path that may need rebalancing.

After removing the key, I repair underfull pages from the bottom up. I first try borrowing an entry from the left sibling, then the right, using only siblings with the same parent. Borrowing moves a boundary entry and updates the parent's separator. I repeat this while needed because moving a tombstoned entry into a full tombstone buffer can trigger another physical removal, leaving the receiving page underfull.

If neither sibling can spare an entry, I merge with the left sibling when available, or otherwise with the right. I keep the left page, move the right page's entries into it, and remove the right child's entry from the parent. For leaves, I also update the next-page link to skip the removed page. The parent may now be underfull, so the repair can continue upward. An internal root with one child is replaced by that child; a leaf root with no stored entries is removed.

### Deferring page deletion until guards are released

I collect pages removed by merging or root replacement in `deleted_page_ids`. While holding the guards, I first update the parent pointers, leaf links, and root ID so these pages are no longer part of the tree. Once rebalancing is finished, I release the header guard and all remaining path guards, then call `DeletePage` for each collected page.

This order matters because a guard both holds a latch and pins the page in the buffer pool. `DeletePage` refuses to delete a page whose pin count is still positive. Keeping the list lets me finish the tree changes while the pages are protected, then reclaim their storage after releasing my guards. If a page still cannot be deleted, the implementation reports an error.

## Index Iterator

My iterator stores a shared pointer to a read guard for the page it is currently reading. To advance the iterator, I first move to the next key-value pair within the current page, skipping tombstoned entries. If I reach the end of the page, I move to the next page using hand-over-hand locking. I acquire the read guard for the next page before releasing the current guard.

## Concurrency Control

I acquire locks from the top of the tree to the bottom and from left to right when locking leaf pages. I follow the top-to-bottom order when traversing the tree for search, insertion, and deletion. I follow the left-to-right order when scanning with the iterator and when borrowing or merging entries between siblings. During traversal, I release ancestor guards once I have acquired the next guard and confirmed that the operation no longer needs those ancestors.
