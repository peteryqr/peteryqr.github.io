## IntermediateResultPage

`IntermediateResultPage` stores variable-length tuples in one page. The page begins with a tuple count and the end offset of free space. Four-byte slots grow forward from the header; each slot stores a tuple's offset and length. Tuple bytes are packed backward from the end of the page. Insertion checks that the next slot and tuple both fit before changing the page. A slot index gives constant-time access to its tuple, and `GetTuple` copies the bytes so the tuple remains valid after its page guard is released. The page stores offsets rather than pointers, so it can be written to disk and read back safely. Space is fixed at one page, with four bytes of slot overhead per tuple plus the four-byte header.

## Pipeline Breakers

Aggregation, hash join, external merge sort, and window functions are pipeline breakers in this implementation. Their `Init()` methods consume input needed to finish the operation; `Next()` then emits completed output in batches while keeping its position between calls.

### Aggregation

Aggregation reads its child into an in-memory hash table keyed by the `GROUP BY` values. `Next()` walks the completed groups. An empty global aggregation still emits its initial aggregate row, while an empty grouped aggregation emits no rows.

### Hash join

Hash join partitions both children into temporary pages during `Init()`. `Next()` loads one left page into an in-memory hash table, scans the matching right partition, and retains probe and match offsets across output batches. For a left join, it also tracks which build rows matched so it can emit NULL-extended rows. Processing one build page at a time bounds the hash table's memory use, although a large partition can require rescanning its right pages.

### Sort and window functions

External merge sort creates sorted runs during `Init()` and merges pairs of runs until one remains. Window functions read and sort their input, compute each partition's results, and materialize output rows during `Init()`. Both emit those completed results incrementally from `Next()`; the window executor keeps its input and output in memory.

## External Merge Sort

The sorter packs tuples into an intermediate page to determine how many fit in each initial run, sorts each run in memory, and writes sorted tuples to pages allocated through the buffer pool. It repeatedly merges adjacent pairs of runs. Each merge holds the current tuple from each input and writes a new run, so it does not pin every page or load the full input into memory.

Each run owns its page IDs. After a merge finishes, the input runs are unpinned and their pages are deleted. The final run is read through an iterator that copies each tuple before releasing its page guard. The final pages are deleted after output is consumed, and `Init()` or error cleanup also releases pages from an earlier or incomplete run. The executor is instantiated only for two-way merging (`K == 2`). A K-way version would keep one current tuple per input run and use a min-heap to choose the next tuple, while reserving buffer space for each input and the output page.

## Leaderboard Optimizations

### Q1

I did not add optimizations for Q1.

### Q2: simplifying aggregates and empty joins

For Q2, I added three passes in order:

1. `OptimizeConstantFilters` replaces supported constant-false or NULL filters with empty Values nodes, so `WHERE 1 = 2` makes the right input empty.
2. `OptimizeColumnPruning` combines adjacent projections, removes unused aggregate results, and reuses identical aggregates through one output-index mapping. For example, repeated `MAX(v1)` calls share one slot, while an unused `MIN(v1)` is removed. I keep all `GROUP BY` keys because they determine which rows belong together.
3. `OptimizeRemoveEmptyJoin` removes an empty-right LEFT join when the parent aggregation uses only left columns.

Q2 then computes just `MAX(v1)` and `MAX(v2)` over the left table and reconstructs the requested expressions in a projection. These rules help queries with unused or repeated aggregates and provably empty join inputs; they do not eliminate joins whose right input may contain rows.

### Q3: Bloom filter for hash join

For Q3, I added a 64 KiB Bloom filter over all non-NULL left join keys during partitioning. I then skip right tuples that definitely cannot match before writing temporary pages, reducing I/O when few keys match. Possible matches still use the exact hash-table lookup because false positives are possible. The filter resets on initialization, and LEFT joins still preserve unmatched left rows.
