## Context and Scope

Projects 1 and 2 provide the buffer pool and B+Tree index. Project 3 connects these storage components to SQL: scans retrieve rows, modification operators change tables and indexes, and joins, aggregation, sorting, and window functions compute query results. The optimizer chooses alternative plans that preserve the result while reducing unnecessary work. See the [original Project 3 specification](https://15445.courses.cs.cmu.edu/fall2026/project3/).

The implementation covers the following operators. Projection, Filter, Values, and MockScan are supporting operators supplied with the query layer; the main P3 work builds on that interface.

| Operator | Role |
| --- | --- |
| SeqScan | Read live table rows and evaluate an optional predicate |
| IndexScan | Retrieve rows through point lookups, composite-key prefixes, or an ordered index scan |
| Insert | Insert child rows into the table and its indexes |
| Update | Replace selected rows and update their index entries |
| Delete | Mark selected rows deleted and remove their index entries |
| Aggregation | Compute `COUNT(*)`, `COUNT(column)`, `SUM`, `MIN`, and `MAX` by group |
| NestedLoopJoin | Evaluate a join predicate for each left/right pair |
| NestedIndexJoin | Probe an inner index for each outer row |
| HashJoin | Partition both inputs and match equal keys using a bounded build table |
| ExternalMergeSort | Sort page-sized runs and merge them through temporary pages |
| Limit | Stop returning rows after the requested count |
| WindowFunction | Compute partition aggregates, running aggregates, and `RANK` while retaining individual rows |
| Projection / Filter | Evaluate output expressions and retain rows whose predicate is true |
| Values / MockScan | Produce literal rows and generated test data |

The factory maps a Sort plan to `ExternalMergeSortExecutor<2>`. The optional TopN and TopNPerGroup executors remain unimplemented, and `OptimizeSortLimitAsTopN` currently returns its input unchanged.

## Execution Model: Top-Down Pull, Bottom-Up Results

The executor follows the **Volcano pull model**. A query plan is a tree, and each executor owns the executors for its children. The execution engine creates this tree through `ExecutorFactory`, calls `Init()` on the root, and repeatedly calls the root's `Next()` until it reports exhaustion. Each operator requests input by calling `Next()` on its children. Control flows from the root down toward the scans; produced rows return from the leaves toward the root.

This version uses **batches of rows**. The interface is `Next(tuple_batch, rid_batch, batch_size)`, and the engine normally requests `BUSTUB_BATCH_SIZE` rows. A successful call returns a nonempty batch, possibly smaller than requested. Exhaustion returns `false`. The pull structure is the same as tuple-at-a-time Volcano, but each call can transfer several tuples. This is the row-based vectorization model described in the [project specification](https://15445.courses.cs.cmu.edu/fall2026/project3/#project-specification).

For example, consider this logical plan before filter/scan merging:

```text
Limit(3)
  Projection(a + 1)
    Filter(b > 10)
      SeqScan(t)
```

The engine asks Limit for output. Limit asks Projection for at most three rows, Projection asks Filter, and Filter reads scan batches until it has enough qualifying rows or reaches the end. The selected values then travel back through Projection to Limit. Once Limit has returned three rows, it stops pulling. A rejected scan batch does not mean the filter is exhausted; it may need to read several more batches to produce output.

### State between batches

An executor must remember where it stopped. A scan keeps its iterator position; a filter keeps an input batch and offset; a join keeps the current input rows and any matches still waiting to be emitted. I advance offsets before returning a row so that filling an output batch does not repeat the last match on the next call. A final partial batch must still be returned before reporting exhaustion.

`Init()` resets execution state and initializes children as needed. This also supports restarting an operator: nested-loop join initializes its right child again for every left row. Batch offsets, match flags, and completion flags must describe the new execution rather than the previous one.

Each plan node supplies an output schema. Scans return the original table RIDs alongside tuples so Update and Delete can identify the stored rows. Computed rows, such as join and aggregate results, have no single table RID and use placeholders. Modification operators return one integer count after consuming their input.

### Streaming and pipeline breakers

Projection and Filter can produce output as their children produce rows. Aggregation, hash join, external sort, and window functions perform blocking work in `Init()`: they consume the input needed to establish groups, partitions, or ordering before their parent can receive results. Hash join still performs its page-by-page build and probe work during `Next()`; initialization partitions the inputs rather than materializing the entire join output.

Blocking work also limits early termination. Limit can stop a sequential scan from reading the rest of a table, but a Sort child has already completed its merges during initialization. My IndexScan similarly collects its candidate RIDs during `Init()`, so an early limit saves later tuple fetches without avoiding the initial index traversal.

## Table Access and Modification

### Sequential scan

`SeqScanExecutor` obtains a table iterator from the catalog during initialization. The iterator records an endpoint so that rows appended later do not extend the scan. This matters for an Update parent, which inserts replacement rows while consuming its child.

For each row, I read the metadata, tuple, and RID, then advance the iterator. Deleted rows are skipped. If the plan contains a predicate, only a true result passes; false and NULL both reject the row. The executor continues until it fills the requested batch or reaches the endpoint.

### Index scan

`IndexScanExecutor` supports three access patterns. A complete key uses `ScanKey`, including when the key has several columns. An ordered scan walks the B+Tree from its first entry. A partial prefix lookup seeks to a lower-bound key, filling the unspecified suffix with minimum values, then advances until the indexed prefix changes.

For an index on `(a, b)`, a lookup for `a = 7` begins at `(7, minimum_b)` and stops at the first key whose `a` is not `7`. It does not walk all preceding entries. A predicate on `b` alone cannot supply that leading prefix.

The index's physical key width determines which B+Tree template I use: 4, 8, 16, 32, or 64 bytes. During `Init()`, I collect candidate RIDs and release the index iterators before a parent Update or Delete can modify the index. `Next()` fetches the corresponding table tuples, skips deleted rows, and evaluates the full predicate. An index lookup narrows the candidates; conditions outside the lookup key still need to be checked. Collecting RIDs makes index modification safe from retained iterator guards, at the cost of memory proportional to the candidate count.

### Insert, update, and delete

All three operators consume their child batches and return one row containing the total affected count. A completion flag prevents a later `Next()` call from applying the changes again.

Insert writes each tuple to the table heap, obtains its new RID, and creates an entry in every index on the table. Each index key is extracted in that index's column order. Delete uses the child's RID to set the table row's deletion flag and removes its key/RID entry from every index; the tuple bytes remain in the heap.

Update evaluates all target expressions against the original tuple, marks that tuple deleted, and inserts the replacement with a new RID. It then removes the old index entries and inserts the new ones. Even an unchanged index key needs a new entry because its RID changed. For example, updating only a salary column still replaces an unchanged employee-ID index entry so that it points to the replacement row.

## Aggregation

`AggregationExecutor` consumes its child into an in-memory hash table during `Init()`. The key contains all `GROUP BY` values, and the value contains the running aggregate results. `Next()` walks the completed table and emits grouping columns followed by aggregate columns. A `HAVING` condition is handled by a Filter above the aggregation.

`COUNT(*)` counts every row. `COUNT(column)` counts non-NULL values, while `SUM`, `MIN`, and `MAX` skip NULL inputs and initialize from the first non-NULL value. Grouping treats NULL keys as belonging to the same group, even though a NULL equality in a filter or join does not evaluate to true.

An empty grouped aggregation emits no rows. An empty global aggregation emits one initial row: in this project's implementation, `COUNT(*)` is zero and the other aggregate types, including `COUNT(column)`, are NULL. A nonempty group containing only NULL inputs gives zero for `COUNT(column)`. Keeping the empty-input case explicit also matters to the optimizer: an aggregation over an empty child cannot simply be replaced by an empty result.

The aggregation table stays in memory and grows with the number of groups. It does not spill to the temporary-page mechanism used by hash join and sorting.

## Join Operators

All three join executors support INNER and LEFT joins. Output contains all left columns followed by all right columns. A LEFT join emits a row with typed NULLs on the right only after establishing that the left row has no match.

### Nested-loop join

For each left row, `NestedLoopJoinExecutor` restarts the right child and tests every right row using the plan's join predicate. Only true matches; false and NULL are rejected. I keep both input batches, their offsets, and a flag recording whether the current left row has matched.

If an output batch fills halfway through the right scan, the next call resumes that scan for the same left row. Once the right input is exhausted, I emit a NULL-extended row if required and advance the left input. This handles arbitrary supported predicates, including inequalities, but can examine every pair of rows: O(L × R) predicate evaluations for inputs of sizes L and R.

### Nested-index join

`NestedIndexJoinExecutor` has one child supplying outer rows. It evaluates the outer key expression, probes the catalog's inner index, and fetches the returned RIDs from the inner table. The key expression produces a lookup value, such as department ID `10`; it is not itself a Boolean predicate.

I retain the outer row and the position in its candidate RID list across batches. A NULL outer key cannot match, and deleted inner tuples are skipped. Once all candidates are consumed, an unmatched outer row is preserved for a LEFT join.

The starter optimizer pipeline can select this executor through its index-join rule. My custom pipeline instead applies the hash-join rewrite and does not invoke that index-join rule, so an available index alone does not mean the default plan will use NestedIndexJoin.

### Partitioned hash join

`HashJoinExecutor` hashes the complete join key and writes each input into temporary partitions during `Init()`. Equal keys on the two sides go to the same partition. I use up to 16 partitions, reducing the count for a small buffer pool. The left side is always the build side in this implementation.

During `Next()`, I copy one left partition page into memory and build a hash table mapping keys to lists of tuple positions. I then scan the corresponding right partition. Each right row probes the table and emits every matching left row. Keeping a list preserves duplicates: two left rows and three right rows with the same key produce six joined rows. Hash collisions still require equality checks on every key component.

The executor retains the current right tuple, its match list, and its position within that list when an output batch fills. A flag per build tuple records whether it matched. After scanning the entire right partition, a LEFT join emits each unmatched build tuple with NULL right columns. NULL left keys are retained for that purpose but never inserted into the hash table; NULL right keys cannot match and are discarded.

One left page bounds the tuple payload used by the build table, even when a duplicate-heavy partition cannot be split effectively by hashing. The tradeoff is repeated work: a partition with B left pages requires B scans of its right partition. Hash-table entries, copied keys, and tuple metadata add memory beyond the page's payload. The Bloom filter described below reduces the right-side data written and rescanned when few keys overlap.

## Intermediate Result Pages

Hash join and external sort share `IntermediateResultPage` for variable-length tuples. Each page has this layout:

```text
Header | slot 0 | slot 1 | ... | free space | packed tuple bytes
        slots grow right →          ← tuple bytes grow left
```

The four-byte header stores the tuple count and the end offset of free space. Each four-byte slot stores a tuple's offset and length. Insertion checks that both the next slot and the tuple fit before changing the page. A slot index provides constant-time access to the tuple, including its variable-length string data.

The page stores offsets rather than pointers, so it can be evicted and loaded at a different memory address. `GetTuple` returns an owning copy before the page guard is released. This lets a merge iterator or join probe retain a tuple without pinning its source page. The layout uses one fixed-size page, with four bytes of overhead per tuple plus the header.

## External Merge Sort and Limit

### Producing and merging runs

External sort first packs input tuples into an intermediate page. When the page is full, I extract its tuples and sort them in memory, then write that sorted run through the buffer pool. Using the actual page layout accounts for variable-length tuples and slot overhead when determining how many rows fit.

I then merge adjacent pairs of runs until one remains. For example, five initial runs become three runs, then two, then one; an unpaired run moves to the next pass unchanged. Each merge keeps the current tuple and sort key from each input, writes the earlier tuple to the output run, and advances only that input. It does not load either full run into memory.

The comparator checks sort keys in order, applying each key's direction and NULL placement. Equal keys defer to the next key; if all keys tie, neither tuple compares before the other. The local implementation defaults to NULLs first for ascending order and NULLs last for descending order, with explicit options overriding that choice.

### Owning and reclaiming temporary pages

Each `MergeSortRun` owns its page IDs. After a merge finishes, I delete its input runs' pages. Iterators copy tuple bytes under local guards, so they do not keep pages pinned between accesses. `Next()` reads the final run incrementally and deletes it after producing the last batch. Run destruction, repeated initialization, and exception cleanup also release owned pages, including when a parent stops early.

Hash join follows similar ownership rules: a copied build page can be deleted immediately, a right partition remains until all its left pages have been processed, and cleanup releases any remaining pages. Releasing guards before deletion is necessary because the buffer pool refuses to delete pinned pages.

The sorter implements two-way merging only. Supporting K-way merging would require tracking one current tuple per input and selecting the next tuple with a min-heap, with buffer capacity reserved for the inputs and output.

### Limiting output

`LimitExecutor` tracks the number of rows already emitted. It requests the smaller of the parent's batch size and the remaining allowance, passes tuples and RIDs through, and stops at the limit or child exhaustion. It does not implement an offset. Because it still initializes its child, even a zero limit can incur work in a blocking child's `Init()`.

## Window Functions

A window function computes a value for each input row while retaining those rows. For values `10, 20, 30` in one partition, grouped `SUM` produces one result, `60`. Window `SUM` without ordering attaches `60` to all three rows. With ordering inside `OVER`, my executor computes the prefixes `10, 30, 60`.

During `Init()`, I collect the child rows and stably sort them by the windows' shared ordering, when present. For each window, I build a map from partition keys to row positions, then compute its results into the appropriate output column. Partition keys use the same NULL grouping behavior as aggregation. Different windows can have different partitions while sharing the sorted input.

The supported functions are `COUNT(*)`, `COUNT(column)`, `SUM`, `MIN`, `MAX`, and `RANK`. Without window ordering, every row receives its completed partition aggregate. With ordering, aggregates record the running result at each row. `RANK` keeps the same rank for ties and uses the next distinct row's position for the next rank: values `10, 10, 30` have ranks `1, 1, 3`.

`Next()` emits the materialized result rows in batches. This implementation keeps the input, partition positions, and output in memory. It does not spill window processing or implement arbitrary window-frame boundaries. Ordering inside `OVER` controls the calculation; a query-level `ORDER BY` controls the final result order.

## Optimizer Rules

The optimizer rewrites plan trees before the executor factory builds them. My rules visit children first, then clone or replace the current node. The custom pipeline simplifies projections and constant filters, prunes aggregate outputs, removes eligible empty joins, chooses hash joins, and then applies ordering and scan rules. Rule order matters because one transformation can expose the pattern needed by the next.

### Sequential scan to index scan

After the supplied filter/scan merge exposes a predicate on SeqScan, `OptimizeSeqScanAsIndexScan` collects column-to-constant equalities. It accepts both `a = 7` and `7 = a`, handles conjunctions, and checks each top-level OR alternative against the same candidate index. Every alternative must supply a usable leading prefix. Among eligible indexes, I choose the longest prefix common to all alternatives and remove duplicate lookup keys.

For example, with an index on `(a, b)`:

```sql
CREATE TABLE lookup_demo(a INT, b INT, c INT);
CREATE INDEX lookup_ab ON lookup_demo(a, b);

EXPLAIN (o) SELECT * FROM lookup_demo WHERE a = 7 AND b = 2;
EXPLAIN (o) SELECT * FROM lookup_demo WHERE a = 7 OR a = 9;
EXPLAIN (o) SELECT * FROM lookup_demo WHERE a = 7 AND c > 10;
```

The first query supplies a complete key. The second supplies two prefixes. The third uses prefix `a = 7`, then checks `c > 10` on fetched rows. Repeating `a = 7` in an OR does not duplicate its lookup. A predicate such as `a = 7 OR c = 10` cannot use this index alone because the second branch lacks its leading key.

The supplied ordering rule can also replace a Sort over SeqScan with an ordered index scan when the ascending order columns match the index keys. This avoids explicit sorting; it is separate from my equality/prefix lookup rewrite.

### Nested-loop join to hash join

`OptimizeNLJAsHashJoin` recursively extracts equalities connected by AND. Each equality must compare columns from opposite inputs. I normalize reversed operands and construct one key-expression list for each child.

For example, `l.a = r.x AND r.y = l.b` becomes left key `(a, b)` and right key `(x, y)`. Expressions are evaluated against their own child tuples, so the right-side expressions are remapped to that child's tuple index. If any conjunct is unsupported, such as `l.b < r.y`, I retain the nested-loop join and its full predicate. Converting only the equality while discarding the inequality would change the result.

### Q2: simplifying aggregates and empty joins

Q2 computes many aggregates in a subquery, but its outer query uses only a few outputs. It also LEFT joins an input made empty by `WHERE 1 = 2`. My custom pipeline addresses these costs in order: constant-filter simplification, aggregate pruning and reuse, then empty-join removal.

`OptimizeConstantFilters` evaluates supported Boolean literals and comparisons of same-typed scalar literals. A true filter disappears; a false or NULL filter becomes a zero-row Values node with the original output schema. Emptiness propagates through Filter and Projection, but not blindly through Aggregation, which may still produce an initial row.

`OptimizeColumnPruning` composes adjacent projections so the outer selection directly identifies the aggregate slots it needs. It then removes unused aggregates and reuses matching aggregates through one mapping from old output positions to new positions. The following example comes from my local Q2 design notes:

```text
Old aggregation: [v, MAX(v1), MIN(v1), MAX(v1), MAX(v2)]
Needed outputs:  [slot 0, slot 1, slot 3 + slot 4]
New aggregation: [v, MAX(v1), MAX(v2)]
New projection:  [slot 0, slot 1, slot 1 + slot 2]
```

The unused `MIN(v1)` disappears, and both copies of `MAX(v1)` share a retained slot. Reuse requires the same aggregate kind and matching input-column coordinates and types; computed arguments remain separate. Repeated `COUNT(*)` calls can also share a slot. All grouping keys remain because removing one could merge distinct groups. A projection restores the original output positions when deduplication happens below a parent that still expects them.

After pruning, `OptimizeRemoveEmptyJoin` removes an empty-right LEFT join directly below an aggregation when all its grouping and aggregate expressions use only left columns. The empty right input contributes exactly one NULL-extended row per left row, so taking the left input directly preserves the rows seen by those expressions. Merely leaving right columns unselected would not justify removing a join whose right input may contain matches and duplicate left rows.

This shortened version of the leaderboard query shows the same opportunities:

```sql
EXPLAIN (o)
SELECT v, d1, d2 FROM (
  SELECT v,
         MAX(v1) AS d1,
         MAX(v1) + MAX(v1) + MAX(v2) AS d2,
         MIN(v1) AS unused_min
  FROM __mock_t7
  LEFT JOIN (SELECT v4 FROM __mock_t8 WHERE 1 = 2) AS r
    ON v < v4
  GROUP BY v
) AS q;
```

The resulting plan has this shape, with names simplified for readability:

```text
Projection(v, m1 AS d1, (m1 + m1) + m2 AS d2)
  Aggregation(group_by=[v], aggregates=[MAX(v1), MAX(v2)])
    MockScan(__mock_t7)
```

Here `m1` and `m2` are the two retained maxima. The final projection reconstructs the requested expressions in their original arithmetic order. The scan and both aggregates remain; the savings come from removing unused aggregate state, repeated calculations, and the empty join. I have not measured a before/after runtime improvement for the refactor combining pruning and reuse.

### Q3: filtering hash-join probes before writing pages

For Q3, I added a 64 KiB Bloom filter covering all non-NULL left join keys. While partitioning the left input, I set four bit positions derived from each key's hash. Only after consuming the complete left input do I partition the right input. A missing bit proves a right key cannot match, so I skip that row before allocating space for it in a temporary page.

For example, if the left keys are `{7, 12}`, right keys `7` and `12` must pass. A right key `90` can be rejected when one of its bits is absent. If collisions make all four bits present, `90` passes the filter but is rejected later by the exact hash-table lookup. False positives add work without adding incorrect result rows.

Filtering before materialization saves temporary writes and later probe reads, including repeated reads when a left partition spans several build pages. The filter covers the entire left input, so a right row cannot be rejected merely because its match belongs to a later build page. LEFT joins still retain unmatched left rows, including NULL keys, and initialization clears the filter for reuse.

The fixed bit array adds predictable memory overhead. Its benefit depends on key overlap and saturation: when most right rows may match, it saves little I/O while still adding hashing and bit checks.
