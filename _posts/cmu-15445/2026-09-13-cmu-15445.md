This design document covers my ARC replacer, buffer pool manager, and leaderboard optimizations for Project 1.

**Author:** Yueqi Ren

## Replacer

### State and lookup

The starter code provides four lists to track MRU, MFU, MRU Ghost, and MFU Ghost. MRU and MFU store frame IDs, which map to metadata such as evictability in `alive_map`. MRU Ghost and MFU Ghost store page IDs.

I added `mru_lookup_`, `mfu_lookup_`, `mru_ghost_lookup_`, and `mfu_ghost_lookup_` to map frame or page IDs to iterators in their respective lists. These maps allow efficient lookup when moving entries between lists, avoiding an O(n) traversal.

### Resident lists, ghost lists, and target size

MRU and MFU track resident pages, while the ghost lists track evicted pages. I update the target size in `RecordAccess` according to the ARC policy described in the spec. `Evict` uses this target to choose between MRU and MFU. When increasing the target, I use `min()` to keep it within `replacer_size`, the number of frames.

## Buffer Pool Manager

### Latching and lock order

In my design, `bpm_latch_` protects shared buffer pool metadata, including `page_table_`, `free_frames_`, and each frame's pin count. Each frame also has an `rwlatch_` that protects its data.

When a page guard is destroyed, its destructor calls `Drop()`, which decrements the pin count and marks the frame as evictable if the count reaches zero. This requires `bpm_latch_` because it modifies shared metadata. Therefore, I enforce the order of acquiring the frame latch before `bpm_latch_` whenever both are held. Accordingly, `CheckedReadPage` and `CheckedWritePage` release `bpm_latch_` before acquiring the frame latch, avoiding deadlocks.

### Loading, eviction, and page guards

In `CheckedReadPage` and `CheckedWritePage`, I first check the page table to see whether the requested page is already in the buffer pool. If it is, I return the corresponding page guard. Otherwise, I take a frame from `free_frames_` if one is available. If not, I use the ARC replacer to select a frame for eviction and reuse it. I then send a read request to the disk scheduler and return a page guard after the read completes. The guard manages access to the frame and releases its pin when dropped.

## Memory Footprint

### Memory beyond the frames

Beyond the page data, memory is used for per-frame metadata in `FrameHeader`, the page table, the free-frame list, and the ARC replacer. These structures use O(N) space for N frames.

I also keep sets of in-flight reads and writes to reduce `bpm_latch_` contention, as described below. The disk scheduler uses 128 workers and request queues, and scan bypass uses a four-page buffer per scanning thread.

### Per-page metadata

The current design does not store per-page metadata that grows with the size of the database.

## Leaderboard Optimizations

### Unlocking during scheduler I/O

Initially, `CheckedReadPage` and `CheckedWritePage` held `bpm_latch_` while waiting for disk reads, creating contention among threads. I now release it before calling `future.get()`. Before unlocking, I add the page ID to the in-flight reads set and remove it after I/O completes. Other threads requesting the same page wait for that entry to disappear, avoiding duplicate reads. The in-flight writes set works similarly, allowing eviction writes to complete without holding `bpm_latch_`.

### Multiple-worker disk scheduler

In the initial implementation, one worker processed all requests from a global queue. I increased throughput by using 128 workers, each with its own queue. Requests are distributed in groups of four consecutive page IDs using `(page_id >> 2) % num_workers_`. Reads and writes for the same page go to the same worker and queue, preserving request ordering.

### Light Scan: buffer pool bypass and prefetching

Large scans can evict frequently accessed pages when the scanned data exceeds the buffer pool size. To avoid this, I bypass the buffer pool for scan accesses and use a thread-local four-page buffer, which is destroyed when the thread exits. This improves get throughput by keeping hot pages in the buffer pool. To improve scan throughput, I also prefetch four pages into the temporary buffer. Since scans access consecutive pages, later accesses can use data already read into the buffer.
