## Context and Scope

A database can contain more pages than fit in memory. The buffer pool keeps a limited set of pages in memory and moves data between memory and storage as needed. Project 1 provides this layer for later components, including the B+Tree in Project 2. The required components are an ARC replacer, a disk scheduler, a buffer pool manager, and page guards. See the [original Project 1 specification](https://15445.courses.cs.cmu.edu/fall2026/project1/).

The main challenge is coordinating these components: choose a page to evict, preserve its changes, load the requested page, and prevent another thread from using incomplete data or reusing a frame that is still in use.

## Pages, Frames, and Guards

A **page** is a fixed-size block of database data identified by a page ID. A **frame** is a slot in memory that can hold one page. A frame can hold different pages over time; `page_table_` records which frame currently holds each resident page. For example, evicting page 10 from frame 2 lets frame 2 hold page 20 without changing either page's identity.

Each `FrameHeader` tracks the page ID, pin count, dirty flag, and a reader-writer latch. A **pin** prevents eviction while a caller uses the frame. A **latch** controls access to its bytes: readers can share access, while a writer needs exclusive access. The dirty flag records that the page has been modified and needs to be written back before eviction.

For ordinary buffer pool accesses, a page guard holds the frame's latch and owns a pin. Dropping or destroying the guard releases both. Moving a guard transfers that ownership and invalidates the old guard, preventing the same pin from being released twice.

## ARC Replacement

### Recent accesses and repeated accesses

Adaptive Replacement Cache (ARC) balances recently accessed pages against pages accessed repeatedly. A new page enters the MRU list. Another access moves it to the MFU list; further accesses refresh its position there. Both lists store frame IDs, with metadata in `alive_map_`.

Each resident list also has a **ghost list** containing the IDs of pages evicted from it, without their data. These lists let the replacer learn from misses: requesting a recently evicted page suggests that its side needed more space.

I keep a lookup map for each list, mapping an ID to its list iterator. This avoids searching the whole list when moving a known entry. Eviction can still scan past pinned frames to find an eligible victim.

### Adapting the target and choosing a victim

A hit in the MRU ghost list increases the target size for MRU; a hit in the MFU ghost list decreases it. The adjustment is at least one and can be larger based on the relative ghost-list sizes. I keep the target between zero and the number of frames. In either case, the returning page enters MFU because it has now been accessed again.

When MRU is below its target, `Evict` tries MFU first; otherwise, it tries MRU. It searches from the least recently used end, skips non-evictable frames, and tries the other list if necessary. A victim moves to its corresponding ghost list. If neither side has an evictable frame, eviction fails.

## Buffer Pool Operations

### Fetching a page

For a normal read or write, I first check `page_table_`. On a hit, `AccessFrame` increments the pin count and marks the frame as non-evictable before the caller waits for I/O or acquires its page latch. This prevents the frame from being reused during that wait.

On a miss, I take a frame from `free_frames_`, or ask ARC for a victim. If all frames are unavailable, the checked access returns `std::nullopt`. Otherwise, I remove the old mapping, arrange any necessary writeback, and schedule a read into the frame. I return the page guard after the required I/O completes.

### Writing back and releasing pages

A dirty victim must have its contents preserved before its frame is overwritten. I copy its bytes into a temporary buffer and schedule the write from that copy. A clean victim needs no writeback. The disk scheduler completes requests through promises, and the caller waits on their futures.

Mutable access through a write guard marks the frame dirty. `FlushPage` pins a resident dirty page and holds a read guard while writing it, preventing modification during the flush. When the last guard drops its pin, the frame becomes evictable again. `DeletePage` refuses to remove a page that is still pinned.

## Concurrency Control

`bpm_latch_` protects the page table, free-frame list, and shared metadata updates. Each frame's `rwlatch_` protects its data, and ARC has its own latch for replacement state.

The lock order matters when a guard is dropped: it already holds the frame latch and needs `bpm_latch_` to decrement the pin count and update evictability. A fetching thread must therefore release `bpm_latch_` before trying to acquire the frame latch. Otherwise, one thread could hold the metadata latch while waiting for a frame whose owner is waiting for that same metadata latch. Pinning the frame before releasing `bpm_latch_` keeps it stable during this handoff.

## Leaderboard Optimizations

The [leaderboard workload](https://15445.courses.cs.cmu.edu/fall2026/project1/) mixes sequential scan threads with get threads that read and update pages using a skewed access distribution. Some pages are revisited often, while scans move through many pages in order. The latency-enabled run also makes random I/O more expensive than nearby accesses. My optimizations address three costs: waiting under the shared latch, serial disk requests, and scans displacing frequently accessed pages.

### Releasing the shared latch during I/O

Holding `bpm_latch_` while waiting for disk would make unrelated accesses wait too, including hits on pages already in memory. I instead publish the new page-to-frame mapping and record the read in `inflight_reads_` before releasing the latch. Another thread requesting that page pins the same frame and waits on a condition variable until the read completes. The wait releases the metadata latch, so other pages can still be accessed.

Dirty eviction needs similar coordination. I record the old page in `inflight_writes_`, and requests for that page wait until its writeback finishes before checking the page table. This prevents a reload from reading its older disk contents. The temporary copy keeps the outgoing bytes alive while the original frame is reused for the incoming page. After I/O finishes, I clear the corresponding entry and notify waiting threads.

This separates short metadata changes from long I/O waits. The cost is extra bookkeeping and a page-sized copy for each outstanding dirty eviction.

### Multiple-worker disk scheduler

Releasing the buffer pool latch allows several requests to be outstanding, but a single disk worker would still process them one at a time. I use 128 workers, each with its own queue, to allow requests on different queues to progress concurrently.

The expression `(page_id >> 2) % num_workers_` sends each aligned group of four pages to one worker. Reads and writes for the same page therefore stay in one queue and execute in enqueue order. Grouping nearby pages also keeps a four-page prefetch together, matching the locality favored by the storage backend's latency model.

This trades some parallelism within a group for ordering and locality. Different groups can also map to the same queue, and 128 threads add scheduling and memory overhead; this worker count is an implementation choice, not a claim that more workers always help.

### Light Scan: keeping scans out of the shared pool

A long scan can fill the buffer pool with pages that will not be used again soon, evicting pages that get threads revisit frequently. For `AccessType::Scan`, I first check the shared page table as usual. A resident page uses the normal guard, but a miss reads into a small thread-local buffer instead of allocating or evicting a shared frame.

The private buffer contains four frames and does not participate in ARC. Scan hits on shared frames also skip `RecordAccess`, so a scan does not promote a page as though it were a repeated lookup. The aim is to preserve shared capacity and replacement history for accesses that benefit from reuse.

### Prefetching four pages at a time

The scan buffer holds one aligned group of four pages. For example, requesting page 10 selects pages 8–11. On entering a new group, I schedule all four reads and wait only for the requested page's future before returning it. Later accesses in the group can use reads that have already completed or are underway.

Before reusing a buffer slot, I wait for its previous I/O to finish. The thread-local buffer's destructor also waits for pending reads, preventing a worker from writing into freed memory when the scanning thread exits.

Prefetching is useful when the scan consumes nearby pages; otherwise, it spends I/O on unused data. This path also assumes short-lived scan guards that are released before buffer reuse. Its private copies are not invalidated by later updates in the shared pool, so it does not provide the same coherence as ordinary shared-frame access. Supporting that would require additional coordination.

## Memory Footprint

For N shared frames, the frame metadata, page table, free-frame list, and ARC state use O(N) space beyond the page data. Ghost history is bounded by the replacement policy; I do not keep a permanent metadata entry for every database page.

Additional memory depends on concurrent work: in-flight I/O sets, temporary copies for dirty eviction, worker threads and request queues, and four private pages per scanning thread. The scan buffers therefore hold extra page data beyond the configured N-frame pool.
